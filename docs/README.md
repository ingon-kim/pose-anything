### 3-1. 측정 아티팩트로 판명된 "발견" — **계측 자체를 먼저 의심할 것**

되돌린 것과 다른 범주다. 코드는 멀쩡했고 **측정이 틀렸다.** 둘 다 그 잘못된
숫자로 원인을 지목하고 처방까지 세웠다가 뒤집혔다.

### 3-2. 원인 진술이 데이터와 맞지 않았던 것

기각된 가설(§3)이나 측정 아티팩트(§3-1)와 또 다른 범주다. **측정도 맞고
코드도 맞는데, 잔여 과제에 적어둔 "원인" 이 이 저장소 자신의 데이터와
어긋나 있었다.**

| 적혀 있던 원인 | 데이터가 말하는 것 |
|---|---|
| **"Re-ID: 복귀 매칭이 위치 기반이라 가림 중 이동하면 원래 ID 복구 실패"** | 위치 게이트는 **물체 폭의 2.5배**까지 허용한다(`rescue_buffer=2.5`, 양쪽 박스를 확장한 buffered IoU>0 — keyboard 328mm / gray notebook 355mm). 그런데 기록된 **모든** ID 분실이 **29~153mm** 에서 일어났다 — 한 자릿수 여유다. 원인은 위치가 아니라 **지속시간**이었고 `occlusion_hold`(2026-08-11)로 이미 고쳐졌다. 그 이후 test4/test5 실행 **전부에서 ID 변경 0건** |

**게다가 현행 조건에서는 재현이 원리적으로 불가능하다.** 삭제 한계는
`max_missed(5) + occlusion_hold(12)` = 18 키프레임 = **6.0초**
(`detect_interval=5`, 15fps). 벨트 46mm/s 에서 6.0초 변위는 **276mm** 로
게이트 328mm 안이다 — **타임아웃이 항상 먼저 발화해 위치 게이트가 구속
조건이 될 수 없다.** 위치가 구속이 되려면 `v > 2.5W / t_가림` — 가림 2.6초·
노트북급 물체면 **137mm/s 이상**이 필요하다.

      결국 폐기됐다** — 행수 세기가 그 미지 항을 닫아 버려 분모가 0 이 됐다.
      **구간을 훑기 전에 그 항을 직접 잴 길이 있는지부터 볼 것**이 더 짧은 답이었다
    - **그리고 "오차 0" 을 "항이 없다" 의 증거로 쓰지 말 것 — 상쇄일 수 있다.**
      같은 건에서 *"z=975 군은 depth 기하만으로 폭 **55.01mm**(정답 55.0) — depth
      는 폭을 잃지 않는다"* 를 확정으로 적었다. **아니었다** — 래스터 손실
      **−0.64** 와 corners 부풀림 **+0.65** 가 상쇄된 값이고, 그 군도 참 18.21px
      를 **18행**으로 잰다. → **판별법: 다른 조건에서 같은 분해가 닫히는지 볼 것.**
      z=945 에서는 같은 두 항이 −2.31 / +1.04 로 **−1.27** 을 내고, 그게 보고값
      53.73 과 맞는다 — **항이 없으면 두 조건 다 0 이어야 한다.** 이 착각 때문에
      "마스크가 폭을 깎는다" 가 한 번 더 살아남았다
    - **그리고 같은 양의 두 통계량이 다른 값을 낸다고 "다른 양" 으로 오진하지
      말 것 — 위상·조건 분포를 먼저 물을 것.** 같은 건에서 `−3.03mm`(합성
      **위상평균**)와 `−5.21mm`(실데이터 **고정 위상**)를 보고 *"서로 다른 오차
      예산을 섞었다"* 고 선언했고 **`geometry.py` docstring 에 경고까지 나갔다.**
      아니었다 — 0° 위상 오차는 **−1.79px(21%) / −0.79px(79%)** 둘뿐이고
      위상평균이 **−1.000px** 이라, **평균이 21:79 로 섞였을 뿐 같은 양**이다.
      → **두 수가 갈리면 "다른 양인가" 보다 "조건 분포가 다른가" 를 먼저 물을
      것.** 그리고 **한 조건에서 언 값을 그 조건의 상수로 읽지 말 것** — 관측
      5.24mm 는 21% 뽑기가 카메라 고정으로 얼어붙은 것이고, 79% 쪽이었다면
      2.31mm 였다([subpixel](subpixel_2026-08-25.md) §4-b).
      **경위도 교훈이다: 형제 팀 반박 → 계산 확인 → 양쪽 철회.** 오늘 팀 간
      교차 확인이 오진을 잡은 두 번째 사례다
  - **위 셋은 이웃이지만 같은 것이 아니다.** pooling 은 **표본**을 섞은 것,
    바로 위는 **항**을 섞은 것, 아래는 **게이트가 이미 제거한 표본**이 만든 상관
    이다. 셋 다 "섞으면 신호가 죽는다" 로 뭉뚱그리지 말 것 — **고치는 방법이
    다르다**(씬별로 재기 / 공통 항 빼기 / 현행 게이트 적용 후 재기)
  - **게이트가 이미 제거한 표본이 만든 상관 — 이건 pooling 이 아니다.**
    `시드산포`(반복 적합의 평면 산포)는 **씬 안에서** 재도 네 씬 전부 양수라
    (+0.211 / +0.332 / +0.593 / +0.275) **유일한 생존 후보**였다. 그런데 그 표는
    **문턱 이전 표본의 것**이었다 — 현행 `0.35` 가 자르는 프레임들이 상관을 통째로
    만들고 있었다. **pooling 을 걷어내도 안전하지 않다**는 뜻이고, 깨지는 방식이
    셋이다:
    - **게이트가 이미 자르는 소수 프레임이 상관을 만든다.** test4 는 문턱 0.30
      에서 **+0.812**(n=31) 인데, `0.35` 가 **추가로 자르는 4프레임**을 빼면
      **+0.085**(n=27) 다 — 이미 자르고 있는 것과 **완전한 중복**이라 추가 이득 0.
      그 4개 중 `kf0008` 은 **d_sd 6.4mm 인데 참오차가 0.0mm** 로, **산포가
      크면서 정확한 반례**다(나머지 셋: `kf0010` 21.4 / half 132.5mm · `kf0026`
      35.9 / 643.4 · `kf0027` 108.5 / 529.9)
    - **추정량 자체가 draw 마다 흔들린다.** test2 는 0.30/0.35 에서 **같은
      16프레임 · 같은 thr(6mm)** 인데, 그 **동일 집합**에 draw 만 바꾸면 corr 이
      **+0.008 ~ +0.695** 로 흔들린다(독립 6회가 +0.008~+0.654, 별도 재계산이
      **+0.695** — 재계산이 앞선 범위를 **벗어난 것 자체가 증거**다). 표본 선택이
      아니라 **추정량의 잡음**
    - **씬 안에서 순위가 역전되면 문턱이 아예 존재하지 않는다.** test4 의 최악
      `kf0011`(half **91.1mm**)의 지표값이 1.25~3.14 인데, 더 나은 `kf0017`
      (half 31.7mm)은 **5.28~9.13** 이다. **32mm 를 자르는 어떤 문턱도 91mm 를
      통과시킨다.** 상관계수가 아니라 **이 역전 하나로 게이트가 죽는다**
    나머지 두 씬에는 애초에 신호가 없다: **isaac 은 0.30/0.35 에서 40/40 동일**에
    corr **+0.079**, **test3 은 0.30 에서 11프레임 → 0.35 에서 0프레임**이다.
    그 11개는 half **37~289mm** 로 오차가 전부 큰데 corr 이 **−0.092** 다 — 순서를
    못 매긴다. **원래 표의 test3 `+0.275` 를 근거로 인용하지 말 것**: 그 표본은
    현 문턱에서 전부 사라졌고 남은 것들끼리는 음의 상관이다.
    → 상관을 보고 게이트를 만들기 전에 **(a) 현행 게이트가 이미 자르는 표본을
    빼도 남는지, (b) 같은 집합에 다시 뽑아도 재현되는지, (c) 씬 안 순위가
    단조인지** 를 볼 것. **(a) 가 이 건의 핵심이다 — 문턱 이전 표본으로 잰 상관은
    그 문턱의 추가 이득을 증명하지 못한다.**
  - **게이트에 요구할 것은 순위 능력(AUC)이 아니라 "통과 영역의 최대 오차" 다.**
    rms 의 pooled AUC 는 **0.88** 로 높은데 **최저 사분위(= "최상급 적합") 안에
    참오차 47.32mm** 가 있었다(등급 오염 168표본, 참 평면을 구성상 정확히 앎).
    반면 `절반불일치` 는 AUC 가 더 낮은데도 최저 사분위 **최대 2.82mm · >5mm
    0%** 다. 게이트가 할 수 있는 약속은 줄세우기가 아니라 **"통과시킨 것은 실제로
    좋다"** 하나뿐이다 — **AUC 를 근거로 게이트를 채택하지 말 것.**
  - **포화된 값을 씬 간에 나란히 놓지 말 것.** 잔차 RMS 는 인라이어가
    `|r| < dist_thresh` 안에만 있어 문턱에 묶인다(균등 분포 상한 `thr/√3`).
    폴백(3mm 우선 → 6mm)이 **씬마다 다른 문턱**을 고른 첫 표본은 포화도가
    **75~98%** 로 전부 상한 근처였다 — **씬 간 비교가 무효**다(6mm 로 고정해
    다시 쟀다). 인라이어도 절대 척도가 아니다: 기준선이 씬마다 다르다
    (isaac 0.51 / test2 0.43 / test4 0.42 / test3 0.25). **문턱 0.35 는 "모든
    씬에서 나쁜 것만 자르는" 값이지 절대 품질 척도가 아니다** — 씬 간에
    0.35 를 인용하지 말 것
  - **관측량을 잘못 고르면 딴 것을 잰다(지렛대).** 평면 `d` 는 카메라 원점까지
    외삽한 값이라 링 중심의 측방 오프셋만큼 기울기 지터가 증폭된다
    (`δd = δn·c_xy`; 합성 예측 0.10mm = 실측 0.10mm). 그래서 **test2 의 ±13.1mm
    는 평면 품질이 아니라 지렛대일 수 있다**(위 허용치 항목). 써야 할 변수는
    **물체 발밑 평면 높이** — OBB 두께가 실제로 소비하는 값이 그것이다.
    → **산포를 보고할 때 "무엇의 산포인가" 가 소비 지점과 같은지 볼 것**
  - **"자신 있게 틀린" 것은 잔차가 작다.** RANSAC 이 오염 구조에 붙으면 그
    부분집합에 아주 잘 맞는다 — 잔차 통계는 *"몇 점이 얼마나 잘 붙었나"* 만 보고
    *"이게 벨트냐"* 는 안 본다. 참값 있는 합성에서: `lip`(참오차 **15.51mm**)의
    rms 1.63mm 가 무해한 `ramp`(참오차 0.81mm)의 1.45mm 와 **0.18mm 차이**고,
    인라이어는 **유해한 쪽이 더 높다**(0.589 vs 0.313). → **적합 품질 지표로
    "맞는 대상에 붙었나" 를 물으면 안 된다.** 이게 rms 가 실기 test2/test4 를 못
    가른 이유이고, 표본 수 문제가 아니었다
  - **산포를 줄이는 후처리는 탐지하지 고치지 못한다.** K=21 median-of-K 의
    참오차가 단발과 같다(**12.65 vs 14.45mm**) — 지배 모드가 틀린 모드면 median
    은 그 틀린 답을 **결정론적으로** 낸다. **"median 으로 산포 5배 감소" 만 보고
    채택하면 조용히 틀린 값을 고정 출하한다.** 산포 감소는 채택 근거가 아니다
  - **"비용 때문에 못 쓴다" 로 기각하기 전에 판별력부터 볼 것.** 이 자리에는
    `시드산포` 를 두고 *"실행당 R회 적합이 필요해 단발 게이트로 못 쓴다"* 라고
    적혀 있었다. **틀렸다 — 비용은 반대 근거가 아니었다.** `fit_plane` 1회가
    3.91(isaac) / 5.37(test2) / 5.68(test4) / 6.12ms(test3), R=21 이 82.1 /
    112.9 / 119.2 / 128.5ms 인데 `_plane_tried` 때문에 **실행당 한 번**이라
    무시할 만하다. 진짜 기각 이유는 **판별력이 없다**는 것이다(바로 위 세 항목).
    덧붙여 이 지표는 씬 **안에서 사실상 상수**다(isaac 0.12~0.22 / test4
    0.69~1.4 / test2 1.95~4.32) — 프레임 판별이 아니라 **씬 블랙리스트**다. 문턱
    스윕에서 test4 를 확실히 낮추는 유일한 값 **0.80mm 는 test2 를 0/16 으로
    전멸**시켜, 저장소가 이미 거부한 `0.45`(test2 7/16)보다 나쁘다.
    **비용은 재면 끝나는 질문인데, 이 건은 비용이 무죄였고 지표가 유죄였다.**
    - **이름 주의 — `시드산포` 계열 수치가 세 곳에 다른 값으로 있다.** ①
      `fit_plane` docstring · 위 허용치 항목의 **±0.40 / ±2.98 / ±13.1mm**,
      ② R=21 실측 평면 `d` 표준편차 **0.18 / 0.94 / 2.58mm**,
      ③ [belt_plane](belt_plane_2026-08-21.md):252 표의 **`1.811d` / `3.405d`**.
      **씬 순서만 같을 뿐 서로 바꿔 쓸 수 없다** — 어느 표에서 온 값인지 같이
      적을 것(③ 의 `d` 접미 단위는 문서에 정의가 없다)
  - **결국 단발 게이트로 쓸 지표는 남지 않았다 — 그런데 결론은 "평면 품질은 못
    잰다" 가 아니라 "이 계측기의 분해능으로는 그 질문에 답할 수 없다" 이다.**
    위 판정들이 전부 기대는 오차 대리값 `half_disagree` 자체가 흔들린다:
    - 같은 프레임에서 **draw 마다 1.5~2배** (test2 `kf0000` 6회 재측정
      **20.96 ~ 37.62mm**)
    - **과대보고 배율 최대 10배** (합성 참 3.67mm → 보고 36.70mm)
    - **무게이트 최대오차가 재는 쪽마다 다르다** — test2 **82.3** / test4
      **91.1mm** 인데 `fit_plane` docstring 표는 **58 / 34mm** 다
    → **`598 → 34mm` 같은 수치를 절대값으로 인용하지 말 것.** "그 34mm 가 더
    주는가" 는 **이 계측기로는 답이 안 나오는 질문**이고, 그것 자체가 지금 문턱을
    더 조이지 말아야 할 이유다. 같은 수치가 §3-1 과 §4 에도 있으니 그쪽을 인용할
    때도 이 단서를 같이 달 것
  - **같은 우산의 마지막 변형: 문서·docstring 도 주장이다.** `compute_obb` 의
    "PCA-based ... via Open3D" 한 줄 때문에 틀린 가설이 하나 섰다. 사례와 결론은
    **§3-1 공통 교훈**에 있다(*"코드가 무엇을 하는지 문서가 아니라 소스에서
    확인할 것"*) — 여기서 반복하지 않는다

  - 게이트를 켜고 뽑은 CSV 로 게이트를 정하려던 것 — 바로 위 항목
  - **`ROS_DOMAIN_ID` 를 격리하지 않고 bag 을 돌린 것** (2026-08-25, 실행 관측).
    **Isaac Sim 브리지가 켜져 있으면 노드가 구독하는 바로 그 토픽으로 다른
    해상도의 `camera_info` 를 쏜다** — bag 과 번갈아 도착해 서명이 매번 바뀌고,
    노드가 매 프레임 리셋해 **출력이 전량 폐기된다**(CSV 헤더 1줄). 에러도
    크래시도 없고 `camera_info changed ... tracker reset` 만 반복 찍힌다.
    → **bag 을 돌릴 때는 `ROS_DOMAIN_ID` 로 격리할 것.** `77` 로 격리하니
    발화 0회 · CSV 63행이었다. **Isaac 과 bag 이 둘 다 이 프로젝트의 입력이라
    Isaac 을 켜둔 채 bag 을 돌리는 사람은 반드시 만난다.** 사례는 §3-1
  같은 부류의 코드 결함도 하나 있었다: **지연 프레임 드롭 락아웃**(§2
  `LATE_DROP_STREAK_MAX`). 노드는 살아 있고 에러도 로그도 없이 드롭만 반복했다.
  → **"에러가 없다" 는 "맞게 돌고 있다" 가 아니다.**
