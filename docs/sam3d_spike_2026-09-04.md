# SAM 3D Objects 스파이크 (2026-09-04)

**질문:** Meta `facebook/sam-3d-objects`(이미지 한 장 + 마스크 → 3D 가우시안/메시,
가려진 부분도 완성)를 지금 GPU(RTX 4070 Ti 12GB)에서 돌려 우리 depth 점군과
정렬한 amodal 3D 출력을 실제로 낼 수 있는가.

**답:** 환경은 완전히 준비됐고 실행도 됐다. 그러나 **물체 1개를 40분 이상 돌려도
디코드가 안 끝났다**(판정선 ≤10초의 200배). **보류 — 32GB 이상 GPU가 생길 때까지.**
`align.py`/`report.py`(ICP 기반 스케일·자세 정렬, amodal 비율 계산)는 설계는
끝났지만 **출력이 하나도 안 나와 실데이터로 한 번도 못 돌렸다**.

측정 환경: RTX 4070 Ti 12,282 MiB, conda env `sam3d-objects`(python 3.11,
torch 2.5.1+cu121), 체크포인트 `facebook/sam-3d-objects`(HF gated:manual),
입력 `bags/test4` 프레임 0000 "black bag" 1개(640×480).

## 1. 요구사항 대 우리 GPU

공식 설치 문서(`doc/setup.md`, Prerequisites) 원문: "A NVIDIA GPU with at least
32 Gb of VRAM." — minimum/recommended 구분 없이 그냥 요구사항으로 적혀 있다.
우리 GPU는 **12,282 MiB** — 격차 2.6배. `environments/default.yml`이 conda 환경
안에 `python=3.11.0`, `cuda-toolkit=12.1.1`, `gcc/g++=12.4.0`을 통째로 박아 두고
그 안에서 `pytorch3d`/`gsplat`을 소스 빌드하는 구성이라, 시스템 torch
2.10.0+cu128·nvcc 13.1과는 별도로 conda 환경을 격리해야 했다.

## 2. 설치

- 실제 실행: conda(26.1.1) 경로, `mamba env create -f environments/default.yml`
  → `pip install -e '.[dev]'` → `.[p3d]`(pytorch3d·flash_attn 소스 빌드) →
  `.[inference]`(kaolin·gsplat·gradio) → `./patching/hydra`.
- **버그 2건 수정**(최소수정, 로직 변경 없음): ① `.env` 없으면 즉시 exit하던
  로직을 캐시된 HF 로그인으로 폴백하도록 변경. ② `./patching/hydra`를 그대로
  실행하면 shebang(`#!/usr/bin/env python`)이 시스템 python을 잡아
  `ModuleNotFoundError: No module named 'hydra'`로 죽음(hydra는 conda env
  안에만 설치) — `$PYRUN python ./patching/hydra`로 수정.
- **설치 자체(pip 3단계)는 전부 성공**했다 — pytorch3d·flash-attn 소스 빌드,
  kaolin·gsplat 설치 전부 통과. 단 `PIP_EXTRA_INDEX_URL`의
  `pypi.ngc.nvidia.com`이 이 환경에서 DNS 해석이 안 돼(`Name or service not
  known`) 패키지마다 5회 재시도 후 기본 PyPI로 폴백 — 기능은 안 깨지지만 **이
  구간에서만 약 70분+**(runner_log.md 추정, 원인은 네트워크 DNS로 스크립트
  버그 아님, 고치지 않음). hydra 패치 전 1차 실행은 여기서 죽었고(`set -e`),
  패치 후 2차 실행은 이미 설치된 부분을 스킵하고 빠르게 통과.
- **환경 import 검증**(pip exit 0만으로는 컴파일 확장 로드를 보장 못 함 —
  advisor 지적으로 추가): conda env `sam3d-objects` 안에서 직접 확인 —
  torch 2.5.1+cu121(`cuda.is_available()=True`), `from pytorch3d import _C`
  OK, gsplat OK, kaolin OK(warp 1.17.0이 RTX 4070 Ti 정상 인식), flash_attn
  OK, hydra 1.3.2. **체크포인트만 받으면 바로 추론 가능한 상태였다 — 이건
  추정이 아니라 확인된 사실.**

## 3. 체크포인트

`facebook/sam-3d-objects`는 HF에서 `gated:manual` — 자동 승인이 아니라 사람이
검토하는 게이트다. `HF_TOKEN`이 유효해도 계정이 미승인이면 403으로 죽는다
("Access to model facebook/sam-3d-objects is restricted and you are not in
the authorized list."). `ingon1` 계정으로 승인 요청 → **16:38경 승인 확인** →
전체 재설치 없이 다운로드 블록만 재실행.

**31개 파일, 7분 26초, 총 13GB** → `checkpoints/hf/`로 정상 이동 확인
(`pipeline.yaml` 포함, 8개 `.ckpt`: ss/slat 각각 generator·encoder·decoder,
slat 쪽엔 `_gs`/`_gs_4`/`_mesh` decoder가 따로 있음). `ss_encoder.safetensors`만
0바이트 — HF 원본 리포 자체 특성으로 보임(`ss_encoder.ckpt`는 119MB 정상,
다운로드 에러 로그 없음).

## 4. 추론 API — 좌표계는 정규화, metric이 아니다

기본 경로(`notebook/inference.py`의 `Inference.__call__` → `inference(image,
mask, seed=42)`)는 카메라 내부파라미터 K를 어디서도 안 읽는다
(`inference_pipeline.py`의 `run()` 전문 확인). 이미지 한 장에서 절대 크기를
알 방법이 없으므로 출력 `rotation`/`translation`/`scale`은 **카메라 방향은
맞지만 스케일은 임의(정규화)**로 결론 내린다 — 우리 depth 점군으로 사후
정렬(`align.py`)이 필요한 이유다.

별도 경로 `InferencePipelinePointMap`(`inference_pipeline_pointmap.py`)은
`pointmap`(3,H,W 텐서, PyTorch3D 카메라 좌표계, **metric 단위로 기대됨**)을
받고 K를 실제로 읽는다(`output.get('intrinsics')`,
`infer_intrinsics_from_pointmap`) — **이게 K를 받는 경로다, 있다. 단 기본
데모 경로가 아니라 이 서브클래스를 통해서만.** 이번 스파이크는 이 경로를
쓰지 않고 K 없이 돌린 뒤 `align.py`에서 depth로 사후 정렬하는 쪽을 택했다 —
**다음 스텝 후보로 강하게 추천하지만 미검증**(우리 depth를 pytorch3d
좌표계 pointmap으로 변환해 이 경로에 바로 넣으면 ICP 없이 metric 출력을
받을 수 있을 것으로 보이나, 이번 스파이크 범위 밖).

## 6. 도구 (`~/sam3d/spike/`)

`run.sh BAG "prompts"`가 4단계를 순서대로 돈다:

1. **`extract.py`**(시스템 python3, GPU 사용 — SAM3 검출) — bag에서
   프레임/마스크/점군/우리 OBB를 뽑는다. **실행 확인**: 12프레임(0000~0011)
   저장, `frames/`·`masks/`·`points/`·`meta.json` 전부 생성됨. `meta.json`의
   `objects[].obb_extent_mm`/`obb_center_m`이 우리 파이프라인 `compute_obb`
   기준값이다(예: 0000 black bag 482.7×516.4×169.7mm).
2. **`run_sam3d.py`**(conda env, GPU 사용) — SAM 3D Objects 추론 실행,
   `splat.ply`/`centers_cam.npy`/`layout.json`/`timing.json` 저장. **§5의
   중단으로 실제 출력 파일은 0건.**
3. **`align.py`**(시스템 python3, GPU 안 씀) — 설계만 있고 **실데이터로 검증
   못 했다**(입력이 될 위 2번 `run_sam3d.py` 출력이 없어서). 설계 요지: 회전 초기값을
   정육면체 고유회전 24개로 시도(단순 yaw 4~8개로는 SAM 3D Objects
   좌표계의 축 맞바꿈을 못 잡는다는 판단), ICP는 **우리 점군을 source, 모델을
   target**으로 등록(반대 방향은 완전한 모델의 안 보이는 뒷면 때문에 fitness가
   축소 편향을 갖는다는 설계 이유 명시), 스케일 붕괴 방지로 `s_icp`가
   `[0.5, 2.0]` 밖인 후보는 기각.
4. **`report.py`**(시스템 python3, GPU 안 씀) — 프레임×라벨 결과를 마크다운
   표로 요약. 마찬가지로 **미검증**(입력 없음).

## 7. 결론

**보류 — 32GB 이상 GPU가 생길 때까지.** 4070 Ti 12GB에서 물체 1개가 40분
이상(판정선 ≤10초의 200배). 환경(conda env `sam3d-objects`, import 검증
완료)·체크포인트·도구는 준비돼 있어 **GPU만 생기면 바로 재개** 가능:

```bash
~/sam3d/spike/run.sh bags/test4 "black bag,keyboard,manual"
```

(프레임 2 × 물체 3 상한 권장 — 전체 12프레임×라벨 조합을 다 돌릴 정도로
빠르지 않다.) 재개 시 2차 과제로 §4의 `InferencePipelinePointMap`에 우리
depth를 metric 포인트맵으로 넣어 ICP 없이 metric 출력을 받는 경로를 검증할
것. 대안: 클라우드 GPU 대여(48GB급) 또는 Spark(GB10 — torch ≥2.9만 지원해
`pytorch3d`/`gsplat` 소스 빌드를 다시 걸어야 하는 도박).

"안 된다는 결론도 좋은 결론" — 이 문서는 그 기록이다.

## 추기 (18:10) — 러너 최종 보고: 스필은 추정이 아니라 확인

- 1차 전체 경로: 모델 로드 13분(DINO 다운로드 포함) → sparse structure 14분 44초 → sparse latent 24분 → **decode_slat 진입 직후 프로세스 종료**(팀 리드가 pid kill). 그 구간 내내 nvidia-smi 11,947~11,965 / 12,282 MiB(97~98%).
- `dmesg`: 커널 OOM killer 아님(시스템 RAM 10 GiB 여유). 대신 `misc dxg: dxgkio_make_resident: Ioctl failed: -12`(ENOMEM) 다수 — **WSL2 GPU 가상화 레이어의 메모리 확보 실패**. 본문의 "시스템 RAM 스필 추정" 은 이 로그로 확인됐다.
- `--stage1-only --max-objects 1` 재시도: 크래시 없이 11분 53초 완료, 그러나 `torch.cuda.max_memory_allocated()` **피크 14,877 MB — 물리 12,282 MiB 초과**(오버서브스크립션에 의존). 출력은 sparse structure 뿐, 가우시안 0개(`no_gs_in_output`) → align/report 산출 불가.
- 체크포인트 자체가 ss_generator 6.69 GB + slat_generator 4.9 GB = 11.6 GB 라 활성화 메모리 여유가 없다. **배치·해상도로 메울 격차가 아니다.** 결론(≥32 GB GPU 전까지 보류) 변경 없음. 로그: `~/sam3d/out/test4_stage1only.log`, `~/sam3d/out/runner_log.md`.
